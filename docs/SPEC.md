# たまにPDF — 仕様書 (v0.12.2)

> たまに使うPDFツール

## 1. コンセプト

仕事やプライベートで **たまにPDFを操作したいだけ** の人のための、ブラウザ完結型ツール。
「インストール不要」「アカウント不要」「アップロード不要」の3点を守る。

- 対象ユーザー: PDF専用ソフトを常用しない一般ユーザー
- 対象デバイス: スマートフォン / タブレット / PC (モダンブラウザ)
- 配信: GitHub Pages (静的ホスティング)

## 2. 最重要方針: PDFはブラウザから出さない

本ツールの根幹は **ユーザーのPDFが絶対にネットワークへ出ないこと**。
これは「そういう運用をしている」ではなく、**技術的に外部送信の経路が存在しない**状態として担保する。

| 担保方法 | 内容 |
| --- | --- |
| サーバ処理なし | バックエンドを持たない。全処理は `pdf.js` / `pdf-lib` によるクライアント処理 |
| CSP `connect-src 'self'` | 外部への `fetch` / `XHR` / `WebSocket` をブラウザレベルで禁止 |
| 依存アセットの自己ホスト | フォント・アイコン・CMap・wasm を含め CDN を一切使わない (外部ドメインへの接続が0件) |
| 解析ツールなし | アクセス解析・エラー収集・広告タグを入れない |
| 保存先はローカルのみ | 設定とテンプレートは `localStorage`。PDFそのものは永続化しない。自動位置合わせ (既定オフ) をオンにしたときだけ、96px幅の白黒簡易画像がテンプレートに加わる (3.3.1参照) |

CSP (本番ビルド時に `index.html` へ自動挿入):

```
default-src 'self'; base-uri 'self'; object-src 'none'; frame-src 'none';
frame-ancestors 'none'; form-action 'none';
script-src 'self' 'wasm-unsafe-eval'; style-src 'self' 'unsafe-inline';
img-src 'self' blob: data:; font-src 'self'; media-src 'self' blob:;
connect-src 'self' blob: data:; worker-src 'self' blob:; manifest-src 'self';
upgrade-insecure-requests
```

- `wasm-unsafe-eval` は pdf.js の画像デコーダ (JBIG2 / OpenJPEG / QCMS) のために必要。
- pdf.js の JavaScript 実行機能 (`enableScripting`) は無効のまま。`isEvalSupported: false` も指定する。
- GitHub Pages は HTTP ヘッダを設定できないため `<meta http-equiv>` で適用する
  (`frame-ancestors` は meta では無効なので、埋め込み防止は別途 JS でも確認する)。

## 3. 機能一覧

### 3.1 ページ整理 (`#/organize`)

1つ以上のPDFを読み込み、ページ単位で編集して1つのPDFとして書き出す。

- ページの **並べ替え** (専用のつまみをドラッグ / 前後へ1つ移動ボタン)
  - つまみだけを掴める形にしているのは、カード全体をドラッグ対象にすると
    `touch-action: none` が必要になり、タッチでの一覧スクロールができなくなるため
- ページの **回転** (90°単位、ページごと / 全体)
- ページの **削除** / **複製** / **選択したページだけを残す**
  - 数十ページから数ページを抜き出すとき、いらないページを1枚ずつ消すのは現実的でないため
  - 履歴に積むので「元に戻す」で戻せる。1ページも残らない指定は受け付けない
- サムネイルの大きさを一覧のツールバーから変更 (小 120px / 中 168px / 大 232px / 特大 340px)
  - 中身を確かめたいだけのために設定画面へ往復させない。変えた値は設定として残る
  - スマホは既定で2列。「大」以上を選んだときだけ1列に落とす
    (2列のままでは、指定を大きくしても実際には大きくならないため)
- **ページの全画面表示** — サムネイルを押すと1ページだけを大きく出す
  - 一覧を大きくする方法では、スマホでカードの枠 (番号・つまみ・チェック・操作ボタン) が
    場所を取り、中身を読める大きさにできなかった
  - ページは 1600px 幅で描いておき、拡大縮小は描き直さずに transform で行う
    (拡大のたびに描き直すと、指を動かしているあいだちらつく)
  - **枠に収まる大きさは画面側で計算して渡す**。CSS の `max-height: 100%` 任せにすると、
    grid の入れ子の都合 (`min-height: auto`) で効かず、紙の下が切れて確かめられなくなる
  - 動かせる範囲も、枠ではなく実際の紙の大きさから決める
  - ピンチ / ダブルタップ / ボタンで 100〜400%。そのまま回転・削除・選択もできる
  - ページ送りは左右に浮かせる。下に並べると小さい画面で折り返すため
  - 表示の列幅は画面幅に固定する (`minmax(0, 1fr)`)。既定の `auto` だと、
    折り返さない見出し (長いファイル名) に合わせて表示全体が画面より広がる
- **追加するページの選択** — すでにページがあるところへPDFを足すとき、中身を見て選べる
  - 最初の読み込みと、1ページのファイル (画像など) は確認しない
  - 設定 `addPagesMode` で「すべて追加する」にも切り替えられる (既定は選ぶ)
  - 複数ファイルを選んだときは、ファイルごとに順番に確認する。
    選択状態はファイルごとに作り直す (前のファイルの選択が残ると、件数と結果が食い違う)
  - 読み込みはファイル単位で確定する。途中で読めないファイルがあっても、
    先に読めたぶんは確認待ちに残す
- ページの **追加**
  - 別のPDFを読み込んで末尾に追加
  - 画像を1ページとして追加 (JPEG / PNG / WebP / AVIF / HEIC・HEIF)
    - JPEG と PNG はそのまま埋め込める。それ以外はブラウザに読ませてから描き直す
      (「元のまま」のときは劣化しない PNG、それ以外は JPEG)
    - 読めるかどうかはブラウザ次第。HEIC/HEIF を読めるのは Safari だけで、ほかでは読めない旨と代わりの方法を伝える。
      HEIC を読むための部品 (libheif。中身は HEVC の展開器) は、HEVC の特許と LGPL の扱いがあるため同梱しない
- **画像で保存** — 選んだページ (選んでいなければ全ページ) を画像ファイルにする
  - 形式: PNG / JPEG (画質90%) / WebP (90%) / AVIF (62)。解像度: 96 / 150 / 300dpi。前回選んだものを覚えておく
  - 1ページなら画像1枚、2ページ以上なら ZIP (少しずつ作る)。ファイル名は「元の名前_p03.png」
    (ページ数の桁に合わせて0を足し、並べたときに順番どおりにする)
  - ページ番号を入れる設定のときは、全体のPDFを組み立ててからそこを画像にする
    (番号は全体の中での位置で決まるため)。番号がなければ読み込んだPDFから直接描く
  - キャンバスが書き出せる形式は、頼んで返ってきた種類で確かめる (書き出せない形式は黙って PNG が返る)。
    Chrome・Safari・Firefox とも AVIF は書き出せないため、Squoosh の AVIF 書き出し器 (@jsquash/avif、Apache-2.0) を
    Web Worker で動かす。GitHub Pages では複数スレッド版の条件 (cross-origin isolation) を満たせないので
    1スレッド版 (wasm 3.4MB) だけを同梱し、AVIF を選んだときにだけ読み込む
  - AVIF の速さ設定は 8 (既定は 6)。A4・150dpi の絵柄のある画像で 2.4秒 → 0.4秒、大きさは同じ (129KB)。
    v0.12.0 では既定のままで、スマホでは1ページに数十秒かかり「0%のまま止まった」ように見えていた
  - 書き出し中は経過秒数を出す。1ページに3分以上かかったら、止まったものとみなして作業役を止め、
    解像度を下げるか別の形式を勧める
  - このブラウザで書き出せない形式は、選べないようにして理由を出す
  - 空白ページを追加 (直前ページと同じサイズ、または A4)
- **画像の取り込み** — ブラウザのデコーダとキャンバスで刷り直してから埋め込む
  - `embedPng` はPNGの展開をすべてJavaScriptで行うため遅い (3MBのPNG1枚で約1秒)。
    `createImageBitmap` → キャンバス → JPEG にすると、同じ処理が数分の一で済み、PDFも小さくなる
  - 設定 `imageImport`: `balanced` (既定・長辺2400px / 画質82%) / `small` (長辺1600px / 画質68%) /
    `original` (元のまま埋め込む)
  - 作り直した結果が元より大きいとき、または作り直せない環境では、元のまま埋め込む
  - 複数ファイルは同時3件まで並行して読み込む (結果は選んだ順に並べ直す)。
    読み込み中は件数の進み具合を出す
  - 実測 (A4 200dpi相当のスキャン風PNG 10枚・計51MB): `original` 16.5秒 / 出力35.7MB、
    `balanced` 1.9秒 / 出力8.4MB、`small` 1.0秒 / 出力2.9MB
- 元に戻す / やり直し (Undo / Redo)
- **一覧の間引き描画** — ページ数が60を超えると、画面に入る行だけを描く
  - 段の数と行の高さは実際に描かれたカードから測る (段組みはCSSが決めるため)
  - 描かない行は同じ高さの余白で埋め、スクロールの長さを保つ
  - 間引くのは見た目だけで、選択・回転・書き出しは全ページが対象のまま
  - 並べ替えは画面に見えている範囲どうしで行う (見えていないカードは掴めない)
- 書き出しは一覧上部のツールバーに置く。ページ数が増えるほど画面末尾は遠くなるため
- **ページ番号の付与** — 位置 (上下 × 左中右の6か所)、書き方 (`1` / `- 1 -` / `1 / 12` / `P.1`)、
  開始番号、文字の大きさ、1ページ目を飛ばすかを選べる
  - 番号はPDF標準の欧文フォント (Helvetica) で描くため、日本語は入れられない
  - ページの `/Rotate` と `/CropBox` を見て、見た目の上で正しい位置・向きになるよう座標を変換する
    (トリミング済みPDFでは、紙のサイズで置くと番号が表示範囲の外に出る)
  - 並べ替えと回転が確定したあと、最後に描く
- 破棄 (クリア) はアプリバーに一本化する。同じ操作を画面内に二重に置かない
- 出力: 元のページ内容をそのまま保持 (再ラスタライズしない)

内部モデル:

```
Source (PDFバイト列)  ──┐
                        ├─> PageRef { sourceId, sourceIndex, rotationDelta }[] ──> 出力PDF
画像/空白 → 1ページPDF ─┘
```

画像と空白ページは読み込み時点で「1ページのPDF」に変換して Source として扱うことで、
ページの扱いを1種類に統一する (拡張しやすさ優先)。

### 3.2 墨消し (`#/redact`)

**方式: 完全ラスタライズ方式**

1. 元のPDFの全ページを画像としてレンダリング (既定 150dpi)
2. 指定された矩形を黒 or 白で塗りつぶす
3. 塗りつぶし済み画像だけで新しいPDFを再構築して出力

テキストレイヤーごと破棄するため、「黒い四角を上に置いただけで下のテキストが残る」
という典型的な墨消し事故が原理的に起こらない。ページ数・ページサイズは維持される。

トレードオフ (ヘルプにも明記):

- 出力PDFは画像PDFになる → 文字検索・テキスト選択はできなくなる
- ファイルサイズが増減する場合がある
- 元PDFのしおり・注釈・フォームは失われる

矩形の座標は **ページに対する 0〜1 の正規化座標** で保持する。
これによりページサイズが違っても同じテンプレートを適用できる。

範囲の編集:

- 作った範囲はタップで選択でき、ドラッグで移動、右下のつまみで大きさを変更できる
  (角がひとつあれば調整できるので、指で押しやすい大きさを優先してつまみは1つに絞っている)
- 表示は 100〜400% まで拡大でき、拡大時はページを描き直して精度を保つ
- 拡大・移動は **2本指の操作**で行う。ピンチで倍率、2本指のドラッグで表示位置。
  パソコンではホイールで移動、Ctrl+ホイールで拡大縮小
- 表示領域の高さは CSS の `aspect-ratio` に任せる。JSで測って高さを決めると、
  その高さでページのスクロールバーの有無が変わり、幅が変わってまた高さが変わる往復が起きる
- 描画に使う解像度は整数段階に丸め、操作が終わってから反映する。
  倍率が変わるたびに描き直すと、同じキャンバスへ二重に描いて絵が壊れる
- 描画は画面外のキャンバスへ行い、出来上がってから一度に転送する (描きかけを見せない)
- 高さには上限を設ける。画面いっぱいに伸びると、その下の操作へ届くまでスワイプが続くため。
  ただし横長の画面では、高さいっぱいに広げて横に操作パネルを並べる (下記 5. 参照)
- 表示はスクロールではなく `transform` で動かす。スクロール頼みにすると、
  拡大時に縦方向へ動かせないなどの取りこぼしが出るため
- 範囲の追加・移動・サイズ変更・削除は取り消し / やり直しの対象。
  ドラッグ中の追従は履歴に積まず、指を離した時点でひと区切りとして積む

### 3.3 墨消しテンプレート

同じ発行元・同じ書式のPDFを繰り返し墨消しするための機能。

```ts
interface RedactTemplate {
  id: string;
  name: string;
  version: 1;
  rects: TemplateRect[];
  createdAt: string;   // ISO8601
  updatedAt: string;
  anchor?: TemplateAnchor;  // 自動位置合わせの基準 (3.3.1)
}

interface TemplateRect {
  x: number; y: number; w: number; h: number;  // 0..1 正規化座標
  color: 'black' | 'white';
  scope:
    | { type: 'all' }                  // 全ページ
    | { type: 'index'; index: number } // 先頭から n ページ目 (0-based)
    | { type: 'fromEnd'; index: number } // 末尾から n ページ目 (0-based)
    | { type: 'odd' }                  // 奇数ページ
    | { type: 'even' };                // 偶数ページ
}
```

- 保存先: `localStorage` (`tamani-pdf:templates`)。書き込みに失敗したら呼び出し側へ伝える
- 読み込み時、範囲が1つでも壊れていたらそのテンプレートは読み込まない
  (「読めたつもりで、隠す範囲が減っている」のを避ける)。未知のバージョンも読み込まない
- JSONファイルとして書き出し / 読み込みが可能 (端末間の持ち運び・バックアップ)

#### 3.3.1 自動位置合わせ

同じ発行元の同じ書式でも、印刷やスキャンのしかたで中身が少しずれることがある。
ずれたまま座標で当てると隠したい文字がはみ出すため、適用前にずれを推定して範囲を動かす。

```ts
interface TemplateAnchor {
  pageIndex: number;        // 基準にしたページ (0-based)
  fingerprint: {            // そのページの縮小画像
    width: number;          // 96px 固定
    height: number;         // 用紙比から決まる (A4 なら 136)
    data: string;           // 8bitグレースケールのbase64 (A4で約17KB)
  };
}
```

手順:

1. 保存時に、そのページを 384px 幅で描いてから 96px 幅へ縮め、白黒画像として持つ
   (いきなり96pxで描くと文字がつぶれて運任せになる)
2. 適用時に、相手のPDFの同じページを同じ手順で画像にする
3. 2枚を重ね、**正規化相互相関**が最大になる平行移動と倍率を探す
   - 粗い画像 (縦横1/2) で当たりを付けてから、元の細かさで詰める
   - 探索範囲は平行移動 ±12%、倍率 0.96〜1.04
   - 最後に放物線あてはめで画素より細かい位置まで求める
4. 相関が 0.55 未満、または用紙の縦横比が3%以上違うときは補正しない
5. 補正した範囲は、推定誤差に備えて各辺 0.4% だけ広げる

設計上の割り切り:

- 傾き (回転) とページごとの個別補正は扱わない。1つのずれを文書全体に当てる
- 補正量と一致度を必ず画面に出す。自動で合ったつもりにさせない
- 96px幅では本文は読めない。ただし大きな見出しなどは判別できることがあるため、
  画面の説明では「文字は読めません」と断定せず「内容の一部が判別できる場合があります」と書く

**既定はオフ** (`templateAutoAlign: false`)。
このツールを使い始める人がまず気にするのは精度よりも「何が保存されるか」なので、
既定では座標だけを保存し、画像を持つかどうかは本人に選んでもらう。

オン / オフで次の表記を切り替える (どちらの状態でも、説明が実態と食い違わないようにする)。

| 画面 | オフのとき | オンのとき |
| --- | --- | --- |
| 設定 | 何が増えるか・どこに置かれるかを説明 | 同上 (常に表示) |
| ヘルプ (プライバシー) | 「保存するのは座標だけ」 | 「簡易画像も入る」 |
| 墨消しのテンプレート保存 | 「座標だけを保存します」+ 設定への導線 | 「簡易画像も一緒に保存します」 |
| 一括墨消し | 「座標のとおりに当てます」 | 「ファイルごとにずれを測ります」 |
| テンプレートのJSON書き出し | 「座標だけが入ります」 | 「簡易画像も入ります」 |

### 3.4 一括墨消し (`#/batch`)

テンプレートを選び、複数のPDFをまとめて処理する。

結果の管理:

- 出来上がったPDFには「どの条件で作ったか」(テンプレート・解像度・形式・画質・自動位置合わせ)
  を持たせる。条件が変わったら、その結果は捨ててやり直しを促す
  — 別のテンプレートで作ったPDFが同じZIPに混ざるのを防ぐため
- 実行中はテンプレートを変更できない
- **当たる範囲が0のPDFは実行しない** (エラーとして止める)。
  「3ページ目のみ」を1ページのPDFに当てるような場合で、
  何も隠れていないのに完了扱いになるのがいちばん危ない。
  この判定は単体の墨消し (3.2) でも同じように行う
- 一部の指定が当たらない場合は、その指定を結果に併記する
- 終了時は「完了○件 / 失敗○件 / 未処理○件」を出す

- 進捗表示 (ファイル単位 / ページ単位)
- 出力: 個別ダウンロード、または ZIP でまとめてダウンロード (`fflate`)
- 1ファイルずつ順次処理 (メモリ使用量を抑えるため並列化しない)

### 3.5 サイズ圧縮 (`#/compress`)

「PDFが大きすぎてシステムの上限に引っかかる」という、たまに使う人がいちばん困る場面のための機能。

**方式**: 墨消しと同じ完全ラスタライズ (`redactToPdf` を「隠す範囲ゼロ」で呼ぶ)。
写真やスキャンのPDFは中身の大半が過剰に精細な画像なので、必要十分な解像度で刷り直すのが
いちばん確実にサイズが落ちる。

- **大きさで決める** (既定) — 収めたい大きさ (1 / 2 / 3 / 5 / 10MB) を選ぶと、
  届くまで強さを一段ずつ上げて試す
  - 段: きれいめ 200dpi/85% → 標準 150dpi/72% → 小さめ 110dpi/60% → とにかく小さく 80dpi/45%
  - 1回の試行にページ数ぶんの時間がかかるため、前の結果から「どう頑張っても届かない段」は飛ばす
    (解像度は面積で効くので二乗、画質は比例とみなし、実際より小さめに見積もって飛ばしすぎを防ぐ)
  - いちばん強い設定でも届かなければ、いちばん小さかった結果と「届かなかった」ことを出す
- **画質で決める** — 上の4段から自分で選ぶ
- 圧縮後は、元と圧縮後の1ページ目を並べて表示する (押すと全画面で確認できる)。
  粗くなりすぎていないかを、保存する前に自分の目で確かめられるようにするため
- **小さくならなかったときは「小さくなりました」と言わない**。
  元のほうが小さい場合はその旨を出し、元のPDFを使うよう勧める
- 読み込み時に先頭3ページの文字量を調べ、文字が多いPDFには先に注意を出す
  (文字が画像になること・かえって大きくなりうること)
- 保存は結果を確かめてから。書き出していない結果があるあいだはタブを閉じるときに引き止める

## 4.5 作業を失わないための決まりごと

このツールはPDFを端末の外へ出さない代わりに、どこにも保存していない。
そのぶん「消えたら終わり」なので、次を守る。

| 場面 | 決まりごと |
| --- | --- |
| 画面の切り替え | 作業中の画面 (整理・墨消し・一括) は消さずに隠す。読み込んだPDFと編集内容はそのまま残る |
| 隠れている画面 | アプリバーへのボタン差し込みとダイアログの表示を止める (前面の画面と混ざらないように) |
| 別のPDFへの切り替え | 消えるもの (指定した範囲) があるときは、先に確認する |
| タブを閉じる・再読み込み | 読み込んだPDFがあるあいだは `beforeunload` で引き止める |
| 端末への保存 | 失敗したら必ず伝える。「保存しました」と出したのに消えている状態を作らない |
| 取り消しの導線 | ページが無くなっても、戻せる履歴があるあいだは「戻す」を出し続ける |
| 書き出したあと | 書き出してから変えていないあいだは引き止めない (保存済みを未完了に見せない) |

ダイアログは開いた瞬間だけ焦点を移し、以降は操作に任せる。
`onClose` のような毎回作り直される関数を効果の依存に入れると、
入力のたびに焦点が飛んでしまうため。開いているあいだは Tab を内側で回し、
閉じたら開くのに使ったボタンへ戻す。

## 4.6 処理の速さ (端末に合わせる)

### 画像化 (墨消し・サイズ圧縮・一括墨消し) をレーンに分けて流す

1ページの仕上げには3つの持ち場がある。

| 持ち場 | どこで動くか |
| --- | --- |
| PDFの解釈・埋め込み画像の展開 | pdf.js の作業役 (Web Worker) |
| キャンバスへの描画 | 画面のスレッド |
| JPEG への書き出し (`canvas.toBlob`) | ブラウザの画像処理スレッド |

1ページずつだと、1つが動くあいだ残りは待つ。数ページを同時に流し (レーン)、
描画・次のページの解釈・前のページの書き出しを重ねる。結果はページ番号の位置に置き、
最後に順番どおり組み立てるので、出力は1ページずつのときと同じ。

計測 (4コア・GPUなし、8ページ・150dpi、開発ビルド、2回の速いほう):

| PDF | 1レーン | 2レーン | 3レーン | 2レーン (作業役2つ) | 3レーン (作業役2つ) |
| --- | --- | --- | --- | --- | --- |
| スキャン風 (PNG) | 1197ms | 954ms | 885ms | 1029ms | 973ms |
| 写真 (JPEG) | 2168ms | 1627ms | 1573ms | 1882ms | 1712ms |
| 文字と線 | 1334ms | 1116ms | 1196ms | 1358ms | 1382ms |

- **作業役 (pdf.js の Web Worker) は1つのまま**にする。レーンごとにPDFを開き直して作業役を増やすと、
  開き直す手間が上回って遅くなった
- 自動の同時数: コア6以上は3、3以上は2、それ以外は1。メモリ (`navigator.deviceMemory`) が
  1GB以下なら1、2GB以下なら最大2 (1レーンあたり A4・150dpi で約9MBの描画面を持つため)
- 設定 `parallel` で 1〜4 に固定できる

### 画像の取り込みを Web Worker で

`createImageBitmap` → `OffscreenCanvas` → `convertToBlob` を作業役で行う (`src/core/image/`)。
作業役は必要になったら立て、同時数まで増やし、30秒使われなければ片付ける。
`OffscreenCanvas` が無い環境や作業役が失敗したときは、画面のスレッドで同じことをやり直す。
計測ではスキャン風PNG 10枚 (51MB) で 1.53秒 → 1.33秒。画面が止まる最長時間は
もともと50ms前後で、作業役にしても縮まらなかった (重い処理はもともとブラウザ側で
画面と別に進んでいたため)。効き目は主に処理全体の時間。

### GPU

- 判定: WebGL が作れるか。作れても描画器名が SwiftShader / llvmpipe などのソフトウェア描画なら使えない扱い
- 使うとき: pdf.js の `enableHWA: true` (作業用の描画面もGPU側へ)、自前の描画面も `willReadFrequently: false`
- 使わないとき: すべての描画面を `willReadFrequently: true` (CPU側) に揃え、GPUとの行き来をなくす
- GPUは描くのは速いが、画像として読み戻す (JPEGにする) のが遅い端末もあるため、効き目は端末次第。
  そこで設定に「この端末で速さを測る」を置き、見本のPDF (写真2・文字2ページ、その場で作る) で
  1レーン/自動レーン × GPUあり/なし を2回ずつ測って、いちばん速い組み合わせを選べるようにした
- 開発環境にGPUが無いため、GPUの効き目そのものはこちらでは測れていない
- **測り方 (v0.12)**: 見本は4ページで1回が0.4秒前後と短く、同じ設定でも測るたびに1割前後ぶれた
  (6回測って 0.38〜0.47秒、1位が入れ替わることもあった)。そこで、全部の組み合わせを1回ずつ測る周を3周回し、
  周ごとに順番を逆にして (端末の温まりや充電による偏りを打ち消す)、組み合わせごとに真ん中の値を採る。
  GPUありとなしの差が1割未満のときは「ぶれの範囲」と表示し、いちばん速い組み合わせにはGPUなしを選ぶ
- **v0.10 と v0.12 の GPU の比較**: 実機 (Pixel 8 Pro) で、v0.10 では GPU ありが速く、v0.11 以降は遅くなったとの報告があった。
  描画の処理は v0.10 から変わっていない (変わったのは、できたページの受け渡しだけ)。
  開発環境で Chromium をソフトウェアの GPU (SwiftShader) でキャンバスを GPU 描画させ、両方の版を同じ測り方
  (4通り × 5周の真ん中) で比べたところ、GPU ありの遅くなり方は両版で同じだった
  (CPU 比 1.3〜1.6倍)。版の違いによるものとは言えず、ブラウザの更新など端末側の変化の可能性が高い。
  どちらが速いかは端末と時期で変わるため、「この端末で速さを測る」で決めるのが確か

## 4.7 大きなPDF (ストリーミング処理)

対象: 墨消し・サイズ圧縮・一括墨消し (全ページを画像化する処理)。

### 読む: ファイルを少しずつ pdf.js に渡す

`openWithPdfjs(Blob)` は `PDFDataRangeTransport` を使い、pdf.js の作業役が求めた範囲だけを
`Blob.slice()` で読んで渡す (1回 1MB、先読みなし)。画面側にファイル全体を読み込まず、
pdf.js に渡すための複製も作らない。部分的に読み直せないファイル (一部のクラウド上のファイルなど) で
開けなかったときは、ファイル全体を読み込んで開き直す。パスワードが要るPDFは読み直さない。

pdf.js の作業役は、読んだ部分をファイルと同じ大きさの領域に貯めていく (`ChunkedStream`)。
これは pdf.js の作りで、こちらからは変えられない。

### 書く: ページができた順にPDFの部品を書く (`ImagePdfWriter`)

出力は「1ページ = JPEG画像1枚」なので、pdf-lib で文書全体を組み立てずに、ページができるたびに
画像・描画命令・ページの3部品を書き、Blob にして手放す。最後にページの一覧・目録・情報・索引 (xref) を書き、
Blob をつなげる (中身の複製は起きない)。部品はファイルのどこにあってもよく、順番は最後の
ページの一覧で決まるので、並べて進めたページが前後してできあがっても届いた順に書いてよい。

- JPEG はそのまま `/DCTDecode` の画像として埋め込む (展開し直さない)
- 情報欄 (Producer / Creator) は UTF-16BE の16進文字列で書く
- 設定で PNG を選んだときだけは、PNG をPDFの形に直す処理を pdf-lib に任せるため、従来どおり全体を組み立てる
- 通しテストで、索引の各行がその番号の部品の先頭を指していることを確かめる。
  pdf-lib / pdf.js は索引が壊れていても中身を探し直して開いてしまうため、開けるだけでは誤りに気づけない

### 一括墨消しの ZIP

出来上がったPDFは Blob で持つ。ZIP は fflate の `Zip` + `ZipPassThrough` (圧縮し直さない) で、
各PDFを `Blob.stream()` で少しずつ読みながら作り、部品は 8MB ごとに Blob にまとめて手放す。

### 計測

150ページ・199MB の写真PDF。4コア・GPUなし。ブラウザの全プロセスのメモリ (RSS) の、始める前からの増え方の最大。

| 処理 | v0.10 | v0.11 | 時間 (v0.10 → v0.11) |
| --- | --- | --- | --- |
| 墨消し 300dpi・画質92% (出力 238MB) | +1,675MB | +1,114MB (−33%) | 28.1秒 → 30.0秒 |
| サイズ圧縮 標準 (出力 14MB) | +1,072MB | +891MB (−17%) | 20.3秒 → 21.2秒 |

- v0.10 では、書き出しの最後 (pdf-lib の保存) で出力の大きさぶん、さらに一段増えていた
- 残りの大半は、描画のための作業領域 (高解像度ほど大きく、ページ数によらずほぼ一定) と、
  pdf.js が読んだ部分を貯める領域 (最大でファイルの大きさ) と、出来上がりの Blob (保存するまで要る)
- pdf.js の作業役の貯め込みを数ページごとに片付ける (`cleanup`) 形も試したが、かえって増えたので採らなかった
- ページ整理の書き出しは pdf-lib でまとめて組み立てるため、対象外 (今後の課題)

## 4.8 外部レビュー (v0.12.1 / 28443e6) への対応

指摘はそれぞれ、再現できるかを確かめてから直した。

| 指摘 | 確認 | 対応 |
| --- | --- | --- |
| [高] ファイルを部分的に読めないと、読み込みが終わらず、全体読み込みへの切り替えにも進まない | 再現 (部分読みが失敗するファイルで15秒以上止まったまま) | 部分読みの失敗を受け取る約束を用意し、開く処理と競わせる。失敗したら全体読み込みで開き直す。全部読めなければ失敗として返す |
| [高] 速さの計測がアプリ全体の設定を書き換え、終わると元に戻すため、測っているあいだに変えた設定と食い違う | コードで確認 | 計測は設定に触れず、組み合わせ (同時数・GPU) を処理に直接渡す |
| [中] GPUありがぶれの範囲で最速のとき、同じ同時数のGPUなしに置き換えるだけで、ほかと比べ直さない | 再現 (100 / 105 / 98ms で 105ms を選んだ) | GPUなしのいちばん速いものと比べる。計算を src/core/perf/pick.ts に分け、単体テストにした |
| [中] GPU の設定を変えても、開いてあるPDFには半分しか効かない (pdf.js の enableHWA は開くときに決まる) | コードで確認 | 開いたときの GPU 設定を覚えておき、違うときは画像化の前に開き直す。サムネイルなど表示用はそのまま (見た目は変わらないため) |
| [中] サムネイルが一度失敗すると描き直せない。片付けたあとに、描いていた途中のものが戻ってくる | コードで確認 | 失敗しても待ち合わせから外す。片付けた回数を数え、描いている途中で片付けられたものは捨てる |
| [中] ページを取りに行っているあいだに中止しても、描き始めてしまう | コードで確認 | ページを取ったあとにも中止を確かめる |
| [効率] 設定画面が速さの計測を直に読み込み、入口の JS に pdf.js と pdf-lib が入っている (1.16MB) | 確認 | 計測ボタンを押したときに読み込む。入口は 0.29MB (gzip 91KB) に |
| [効率] 画像の取り込みで、作り直した画像を使うときも元のファイルを全部読む | 確認 | 大きさの比較は file.size で行い、元のまま入れるときだけ読む |
| [効率] 計測が「1」と「自動の同時数」しか比べない | 確認 | 1・2・3 をすべて比べる。工程ごと (開く・描く・画像にする・組み立て) の時間も出す |

## 5. 画面構成

```
#/            ホーム (ツール選択)
#/organize    ページ整理
#/compress    サイズ圧縮
#/redact      墨消し
#/batch       一括墨消し
#/settings    設定
#/help        ヘルプ
```

ハッシュルーティングを使う (GitHub Pages で 404 を出さないため)。
PC は左のナビゲーションレール、スマホは下部ナビゲーションバーに切り替える。
切り替えの条件は **幅 840px 以上 かつ 高さ 600px 以上**。
レールは6項目ぶんの高さ (約470px) を必要とするため、幅だけで判定すると
横向きのスマホでレールが画面の高さを超えてしまう。

### 画面の向きによるレイアウト

墨消しは CSS グリッド (`grid-template-areas`) で2種類の配置を持つ。

| 画面 | 配置 |
| --- | --- |
| スマホ (幅760px未満 **または** 高さ600px未満) | ツールバー → プレビュー → 説明・範囲一覧 の縦積み |
| PC・タブレット (幅760px以上 **かつ** 高さ600px以上) | 左にプレビュー (高さいっぱい)、右にツールバーと各パネル |

左右に分ける配置では、見出しとフッターを畳んでプレビューを高さ基準で拡大する。

判定に高さを含めているのは、横向きのスマホ (例: 844×390) で左右に分けると
どちらの列も窮屈になり、縦積みのほうが扱いやすいため。
スマホは端末を横に倒しても縦長と同じ並びのままになる。

なお、ブラウザから画面の向き自体を固定することはできない
(`screen.orientation.lock()` は全画面表示またはインストール済みPWAでのみ有効)。
そのため「向きに関わらず同じ並びにする」形で対応している。
